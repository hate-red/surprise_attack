# Автозаполнение характеристик СТЕ и подбор кода КТРУ

Веб-сервис: пользователь вводит описание товара на русском языке, сервис находит
наименование в справочнике КТРУ, извлекает и нормализует характеристики, проверяет
значения и единицы измерения по справочнику и поэтапно сужает множество позиций
КТРУ до итогового кода — либо честно сообщает, чего не хватает.

- Backend: FastAPI + SQLAlchemy 2 (async) + PostgreSQL + Alembic (`app/`)
- Frontend: Next.js 16 + React 19 + Tailwind 4 + zustand (`frontend/`)
- Анализ полностью детерминированный: без LLM и внешних API, ответ за десятки–сотни миллисекунд

## Быстрый старт

```bash
# 1. PostgreSQL и миграции
docker compose up -d postgres
docker compose run --rm migrate

# 2. Загрузка справочника КТРУ (все nsiKTRUNew_all*actual*.xml из "initial files/xmls", ~1.5 мин)
docker compose run --rm fastapi python -m app.parser.ktru_importer
# 3. Загрузка характеристик портала поставщиков (xlsx из "initial files", ~5 с)
docker compose run --rm fastapi python -m app.parser.ste_importer

# 4. API на http://localhost:8000 (документация: http://localhost:8000/docs)
docker compose up -d fastapi

# 5. Frontend на http://localhost:3000
cd frontend
pnpm install
pnpm dev
```

Адрес API для фронтенда задаётся переменной `NEXT_PUBLIC_API_BASE_URL`
(см. `frontend/example.env`, по умолчанию `http://localhost:8000`).
Разрешённые для CORS адреса фронтенда — переменная `CORS_ORIGINS`
(по умолчанию `http://localhost:3000,http://127.0.0.1:3000`).

Без Docker: укажите в `.env` `DB_HOST=localhost` (или задайте `DATABASE_URL`),
затем `alembic upgrade head`, `python -m app.parser.ktru_importer`,
`python -m app.parser.ste_importer`, `uvicorn app.main:app --reload`.

Импорт можно повторять: таблицы справочника очищаются и загружаются заново в одной
транзакции. После повторного импорта при работающем API вызовите
`POST /kgru-positions/reload-index` (или перезапустите API).

## Данные

| Источник | Что загружается | Таблицы |
|---|---|---|
| `nsiKTRUNew_all*actual*.xml` (файлы `*not-actual*` игнорируются) | 60 087 позиций со статусом ACTIVE, 234 тыс. характеристик, 679 тыс. значений | `positions`, `characteristics`, `characteristic_values`, `okei`, связи |
| `Инструменты.xlsx`, `Мебель.xlsx`, `Одежда.xlsx` | 527 категорий портала поставщиков, 84 тыс. характеристик | `categories`, `additional_characteristics` |

Значения КТРУ сохраняются ровно так, как заданы в XML:
`qualityDescription` → перечень (качественное значение), `rangeSet/valueRange` →
`NUMRANGE` со строгими/нестрогими границами, `valueSet/concreteValue` → точное число;
единица (ОКЕИ) — у каждого значения. Если в XML ограничений нет, их нет и в БД, и значение
пользователя не считается ошибочным. Справочник КТРУ — первичный источник допустимых
значений; выгрузка СТЕ только помогает распознать формулировку и никогда не влияет на
выбор кода.

Миграция `2b7c4e91d0aa` аддитивная: новые nullable-колонки (ОКПД2, статус, даты
применения, признак шаблона, тип/вид характеристики, точное значение, код ОКЕИ),
индексы по внешним ключам и таблицы пакетной обработки CSV.
`app/parser/ktru_importer.py` заменяет связку `xml_to_json.py` → `ktru_db.json` →
`seed.py`, которая отбрасывала точные значения и все диапазоны, кроме первого.

## Как работает анализ (`app/services`)

1. **Нормализация** (`nlp/text.py`, `nlp/stemmer.py`): регистр, «ё», кавычки и тире,
   десятичные запятые, сокращения («кол-во», «выс.», «д/»), основы слов (стеммер
   Snowball для существительных и прилагательных, беглые гласные «молоток/молотка»)
   и корни («кожаный» ~ «кожа», «сетевая» ~ «сеть»).
2. **Опечатки** (`nlp/spelling.py`): словарь из ~41 тыс. словоформ КТРУ и СТЕ, расстояние
   Левенштейна с перестановками (RapidFuzz OSA). Опечатки не блокируют анализ: они
   подсвечиваются, а исправленный текст предлагается применить.
3. **Наименование** (`ktru_selector.match_name`): индекс 12,7 тыс. уникальных наименований
   с весами IDF; учитываются главное слово, позиция слов в описании и непокрытые слова.
   Затем второй проход: короткий список наименований переранжируется по тому, насколько
   их характеристики и допустимые значения из БД объясняют остальной текст
   («дрель аккумуляторная 18 В» → «Дрель ручная электрическая», а не хирургическая).
4. **Характеристики** (`characteristic_extractor.py`): упоминания названий
   характеристик кандидатов, значения из перечней, числа, интервалы («от 40 до 50»,
   «не менее 3»), габариты «1200x600x750 мм», признаки «с реверсом / без подлокотников».
   Единицы приводятся к единице КТРУ (`nlp/units.py`: все 101 единица ОКЕИ, встречающаяся
   в значениях КТРУ, и ~170 написаний в тексте — «мм», «кв.м», «об/мин», «А·ч», «"» для дюймов), значение
   проверяется по диапазонам каждой позиции: в ответе указан диапазон, в который оно
   попало, а недопустимое значение не попадает в спецификацию. Названия, которых нет ни
   в КТРУ, ни в СТЕ, помечаются как нераспознанные.
5. **Сужение** (`ktru_selector.narrow`): каждая характеристика — отдельный этап с реальным
   числом позиций до и после. Значение, противоречащее уже оставшимся позициям, не
   применяется и помечается. Шаблонная позиция КТРУ уступает единственной конкретной.
   Если позиций больше одной — предлагаются характеристики, значения которых
   различаются у оставшихся позиций.

### Четыре сценария (`status` в ответе)

| Сценарий | `status` | Что видит пользователь |
|---|---|---|
| Данных недостаточно | `need_more_info` | «Попробуйте указать: Тип каркаса, …», кандидаты, кнопки уточнения |
| Код определён | `resolved` | Итоговый код и подтверждение, что информации достаточно |
| Характеристика не распознана | сообщение `unrecognized_characteristic` | «Характеристика «…» не распознана: её нет ни в КТРУ, ни в выгрузке поставщиков» |
| Наименование не найдено | `name_not_found` | Просьба изменить наименование, похожие наименования, кода нет |

Если наименование распознано неуверенно, код не выдаётся (`low_confidence`).

## API

| Метод | Путь | Назначение |
|---|---|---|
| POST | `/kgru-positions/parse?user_input=...` | Анализ описания. Необязательное тело: `{"overrides": [{"name", "value"}], "excluded": [...], "selected_code": null}` — значения, подтверждённые/изменённые пользователем |
| GET | `/kgru-positions/{код}` | Позиция КТРУ с характеристиками и значениями |
| GET | `/kgru-positions/typos?user_input=...` | Проверка опечаток |
| POST | `/kgru-positions/reload-index` | Перестроить индекс после импорта |
| POST | `/batches?filename=...` | Загрузка CSV (тело — содержимое файла, одна колонка описаний) |
| GET | `/batches`, `/batches/{id}`, `/batches/{id}/items/{item_id}` | Статус пакета, строки и результат строки |

Ответ `/parse` — объект `ParseResponse` (`app/schemas/positions.py`). Прежний список
позиций сохранён в поле `positions` (формат `PositionResponse`).

## Интерфейс

Главная страница сохраняет прежнюю раскладку: форма ввода, «Проверка качества»,
«Подбор КТРУ» (реальные этапы сужения, кандидаты, кнопки «Указать…» и «Выбрать»),
таблица «Итоговые характеристики» (редактирование, удаление, добавление, подсказки
допустимых значений) и вкладка исходного текста с подсветкой наименования,
характеристик, нераспознанных фрагментов и опечаток. Кнопка со скрепкой загружает CSV;
панель «Пакетная обработка CSV» показывает прогресс, а строка открывает страницу
`/batches/{id}/items/{item_id}` с описанием и тем же интерфейсом заполнения спецификации.

## Тесты

```bash
python -m unittest discover -s tests -t . -v
```

`tests/test_nlp.py` не требует БД; `tests/test_scenarios.py` проверяет сценарии на
загруженном справочнике (пропускается, если справочник не загружен).

## LLM (необязательно)

`app/services/get_evals.py` — прежний эксперимент с Qwen 3.5 2B + MiniLM. Основной
конвейер его не использует: генерация на CPU не укладывалась в 5–6 секунд. Модели
загружаются только при вызове `load_models()`; зависимости — `requirements-llm.txt`.
